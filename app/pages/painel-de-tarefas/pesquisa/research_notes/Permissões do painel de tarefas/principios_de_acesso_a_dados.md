# Princípios de acesso a dados em painéis de analytics embarcados: quem abre o painel x quais linhas ele conta

Notas de pesquisa para o painel de tarefas fixo e nativo do ENSPACE (SaaS multi-tenant). Todas as fontes foram acessadas em 2026-11-11; a data da página aparece quando ela mostra uma. Trechos entre aspas são curtos e literais; o resto é paráfrase.

## 1. Como Power BI, Tableau, Looker, Metabase e Sisense separam "quem abre o painel" de "quais linhas ele conta", e qual é o padrão documentado

### Takeaway
Os 5 fornecedores tratam as 2 coisas como camadas independentes: a permissão de conteúdo (pasta, workspace, coleção, compartilhamento) decide quem abre; a segurança de linha (RLS, user filter, access filter, row and column security, data security rule) decide o que cada visual soma. O padrão muda de um para outro: Power BI, Sisense e Metabase com atributo errado devolvem vazio para quem não tem regra; Looker deixa a Explore aberta se o `access_filter` não for declarado nela; e o Power BI não aplica RLS a quem pode editar o workspace.

### Cited Findings

**Power BI (Microsoft Fabric)**
- A RLS do Power BI só restringe usuários com permissão **Viewer**; não se aplica aos papéis Admin, Member e Contributor do workspace, porque eles têm permissão de edição no modelo semântico. Para a RLS valer para alguém do workspace, essa pessoa só pode ter o papel Viewer. Página com ms.date 2026-05-13, atualizada em 2026-07-08 — [Microsoft Learn, Row-level security (RLS) with Power BI](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- O filtro DAX avalia TRUE/FALSE em cada linha; só as linhas TRUE ficam visíveis e o resto é removido. Visuais, tabelas e gráficos refletem os dados filtrados, não o conjunto inteiro — [Microsoft Learn, RLS with Power BI](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- Mesmo um Viewer com permissão **Build** (Analisar no Excel, por exemplo) continua restrito pela RLS — [Microsoft Learn, RLS with Power BI](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- Padrão para quem não está em nenhum papel de RLS: o usuário "typically see no data" (resultado vazio), porque a RLS está ativa e nenhum papel casa com ele — [Microsoft Learn, RLS with Power BI, seção de troubleshooting](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- Papéis de RLS são aditivos: quem está em "Sales" e "Marketing" vê os dados dos 2 — [Microsoft Learn, RLS with Power BI, FAQ](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- A RLS não permite esconder o detalhe e liberar só o total: a FAQ responde "No" e diz que o usuário sempre vê o detalhe ou o resumo das linhas a que tem acesso. Para restringir coluna, a Microsoft indica a object-level security (OLS) — [Microsoft Learn, RLS with Power BI, FAQ](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- Service principals não entram em papel de RLS; por isso a RLS não se aplica a apps cuja identidade final é um service principal — [Microsoft Learn, RLS with Power BI, limitações](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)

**Tableau**
- Tableau oferece 5 caminhos de segurança de linha: user filter manual (mapeia usuário a valor, por workbook, "high maintenance"), user filter dinâmico (campo calculado com `USERNAME()` e uma coluna de segurança nos dados), data policy em virtual connections (desde 2021.4, com Data Management; aplicada no servidor em toda consulta e recomendada pela Tableau "in most situations"), RLS do próprio banco (exige consulta live) e user attributes passados num JWT para conteúdo embarcado (connected apps) — [Tableau Help, Overview of row-level security options](https://help.tableau.com/current/online/en-us/rls_options_overview.htm)
- Os user filters dependem da permissão de conteúdo: quem pode salvar ou baixar o asset consegue remover o filtro e ver todos os dados. Por isso as permissões dos assets publicados precisam ser travadas — [Tableau Help, Overview of row-level security options](https://help.tableau.com/current/online/en-us/rls_options_overview.htm)
- A página não declara um comportamento padrão de RLS nem fala do site role Viewer — [Tableau Help, Overview of row-level security options](https://help.tableau.com/current/online/en-us/rls_options_overview.htm)

**Looker (Google Cloud)**
- Looker separa 3 camadas: **content access** (pastas, dashboards e Looks, pelo nível de acesso da pasta; ver exige pelo menos View), **data access** (model sets nos papéis, `access_filter` para linhas e `access_grant` para Explores, joins, views e campos) e **feature access** (permission sets). Um papel é a soma de 1 permission set e 1 model set. As pastas não controlam dado nem ação na plataforma — [Looker docs, Access control and permission management](https://docs.cloud.google.com/looker/docs/access-control-and-permission-management)
- Quem abre um dashboard sem acesso ao modelo de um tile vê esse tile em branco ou com erro, nunca o dado — [Looker docs, Access control and permission management](https://docs.cloud.google.com/looker/docs/access-control-and-permission-management)
- O `access_filter` é declarado por Explore e liga um campo a um user attribute; age como um filtro obrigatório antes de qualquer consulta. Se a pessoa esquecer de declarar em uma Explore, "the data will not be restricted" — [Looker docs, access_filter](https://docs.cloud.google.com/looker/docs/reference/param-explore-access-filter)
- Todo usuário de uma Explore com `access_filter` precisa ter valor no atributo, admin incluído; sem valor, recebe erro ao abrir a Explore. Para o admin ver tudo, a doc indica valores coringa (`%, NULL` em atributo texto) — [Looker docs, access_filter](https://docs.cloud.google.com/looker/docs/reference/param-explore-access-filter)
- Com `access_filter`, as sugestões de filtro passam a respeitar a restrição (`full_suggestions` vira `yes`) — [Looker docs, access_filter](https://docs.cloud.google.com/looker/docs/reference/param-explore-access-filter)

**Metabase (docs v65)**
- Row and column security é o novo nome do data sandboxing. Liga uma versão filtrada da tabela a um grupo, e essa versão substitui a tabela original em todo lugar do Metabase onde ela é usada. Máximo de 1 política por par tabela/grupo. Só nos planos Pro e Enterprise — [Metabase docs, Row and column security](https://www.metabase.com/docs/latest/permissions/row-and-column-security)
- A segurança de linha exige user attribute; o valor precisa casar exatamente (inclusive maiúsculas). Valor que não casa devolve resultado vazio — [Metabase docs, Row and column security](https://www.metabase.com/docs/latest/permissions/row-and-column-security)
- Quem está em 2 políticas para a mesma tabela recebe erro de conflito; a correção é deixar a pessoa em 1 grupo só ou bloquear o acesso dos outros — [Metabase docs, Row and column security](https://www.metabase.com/docs/latest/permissions/row-and-column-security)
- Limites que vazam dado: grupo com permissão de SQL nativo contorna a segurança de linha; perguntas em SQL não são protegidas (a doc manda usar a permissão de coleção para isolá-las); link público e dashboard público não aplicam a segurança de linha e expõem a tabela original — [Metabase docs, Row and column security](https://www.metabase.com/docs/latest/permissions/row-and-column-security)

**Sisense**
- "Each widget only shows the data permitted by the data security rules", incluindo totais e médias; linhas não permitidas saem por inteiro e não entram no total, mesmo quando o campo protegido não está no widget. Um widget compartilhado com outra pessoa continua filtrado pelas regras dela — [Sisense docs, Data Access Security](https://docs.sisense.com/main/SisenseLinux/data-access-security.htm)
- Boa prática: deixar "Everyone else" como "Nothing" e liberar valores a usuários e grupos específicos; não atribuir valor a Everyone equivale a bloquear todos — [Sisense docs, Data Access Security](https://docs.sisense.com/main/SisenseLinux/data-access-security.htm)
- Precedência: o modelo acumula concessões e a combinação mais restritiva vence entre regra de usuário e regra de grupo; a regra padrão só vale quando não há nenhuma das 2 — [Sisense docs, Data Access Security](https://docs.sisense.com/main/SisenseLinux/data-access-security.htm)
- O guia de desenvolvedor da Sisense recomenda a regra padrão "forbid all", para que quem não tem regra não veja dado nenhum — [Sisense developer docs, Data security](https://developer.sisense.com/guides/restApi/data-security.html) (lido no resumo da busca, página não aberta)
- Separada da regra de linha, a segurança do modelo de dados limita o modelo a usuários ou grupos nomeados; ElastiCubes criados depois da V7.0 nascem acessíveis só ao dono — [Sisense docs, Security Architecture](https://docs.sisense.com/main/SisenseLinux/sisense-security-architecture.htm) (lido no resumo da busca, página não aberta)

### Inferences
- Há 3 lógicas de combinação de regras: Power BI soma (união dos papéis), Sisense fica com a mais restritiva, Metabase dá erro de conflito. Um produto próprio precisa escolher uma e declarar.
- O ponto em comum entre os 5: o total de um visual é calculado depois do filtro de linha, no servidor. Nenhum deles oferece "ver o total de linhas que não posso abrir" como recurso de RLS; o Power BI diz isso na FAQ.
- O papel que edita o modelo escapa da RLS no Power BI, e quem pode baixar o asset escapa do user filter no Tableau. A permissão de "abrir a tela" e a de "editar ou exportar" mudam o alcance do dado; quem desenha o painel do ENSPACE precisa listar os 2.
- O padrão "nega quando falta regra" (Power BI, Sisense, Metabase) é o mais próximo do deny by default do OWASP (seção 3). O Looker é o contraexemplo: a regra mora na Explore e o esquecimento abre o dado.

### Gaps
- A página de RLS do Tableau não trata do site role Viewer nem de um padrão; não abri a página de site roles.
- A página do Looker não diz, com essas palavras, que o `access_filter` filtra os tiles do dashboard; a conclusão vem de os tiles rodarem consultas na Explore.
- A doc do Metabase não diz o que vê um grupo sem política na tabela; isso depende da permissão "View data" do grupo, que não abri.

## 2. Guias de analytics embarcado sobre herdar as permissões do app hospedeiro

### Takeaway
No modelo "o app é dono do dado", quem decide a identidade e as regras é o app hospedeiro: ele passa o usuário, o papel, o grupo e os atributos num token assinado, e o motor de BI filtra as linhas com isso. As permissões configuradas dentro do BI para usuários dele deixam de valer, e o embed sem identidade (guest, público) não aplica segurança de linha.

### Cited Findings
- No Power BI Embedded, as opções de isolamento são RLS, OLS e isolamento por workspace (1 modelo semântico por cliente, combinável com RLS dentro do cliente). A Microsoft indica RLS dinâmica num modelo único para ISV pequeno ou médio e workspace por cliente com service principal profiles para ISV com milhares de clientes. Página com ms.date 2025-12-15 — [Microsoft Learn, Security in Power BI embedded analytics](https://learn.microsoft.com/en-us/power-bi/developer/embedded/embedded-row-level-security)
- No cenário "app owns data", atribuir usuários a papéis no serviço do Power BI não afeta a RLS do embed token; quando o token leva uma identidade, as regras dessa identidade valem mesmo que a conta usada seja admin, member ou contributor — [Microsoft Learn, Security in Power BI embedded analytics](https://learn.microsoft.com/en-us/power-bi/developer/embedded/embedded-row-level-security)
- Com service principal, `USERPRINCIPALNAME()` e `USERNAME()` devolvem o id da aplicação ou vazio, não o usuário final; a RLS por usuário exige passar `EffectiveIdentity` (usuário e papéis, e `CustomData` se a regra usar `CUSTOMDATA()`) ao gerar o embed token — [Microsoft Learn, RLS with Power BI, dynamic RLS](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- No Looker signed embedding, o usuário se autentica no app do cliente; a URL assinada define permissões, modelos, grupos e user attributes do usuário embarcado (um "Embedded Role" somado aos grupos). Permissões e atributos não mudam no meio da sessão — [Looker docs, Signed embedding](https://docs.cloud.google.com/looker/docs/signed-embedding)
- O Looker exige `external_user_id` único por usuário: reaproveitar o id "can cause data to be visible" a quem não teria acesso. O `external_group_id` separa as pastas de cada grupo externo, e a doc recomenda o modo Closed System (instalação multi-tenant) antes de liberar usuário externo. A URL assinada vale 5 minutos e leva nonce único contra reenvio — [Looker docs, Signed embedding](https://docs.cloud.google.com/looker/docs/signed-embedding)
- Usuários do signed embedding são sintéticos, gerados pela URL, e não herdam grupos SAML gerenciados fora — [Looker docs, Signed embedding](https://docs.cloud.google.com/looker/docs/signed-embedding)
- No Metabase, o guest embed (antes "static embedding") não usa permissões de usuário nem row and column security, porque não sabe quem está vendo. O controle é o parâmetro **Locked**: o servidor do app grava o valor no JWT e o Metabase aplica o filtro antes de o dado chegar ao navegador. Esconder o widget de filtro não restringe o valor. A chave secreta é a mesma para todos os guest embeds. Para segurança de linha, a doc aponta o "Modular embedding with SSO" — [Metabase docs v65, Guest embedding](https://www.metabase.com/docs/latest/embedding/guest-embedding)
- No Tableau, o embed passa user attributes num JWT por connected apps, e o conteúdo usa funções de user attribute para filtrar — [Tableau Help, Overview of row-level security options](https://help.tableau.com/current/online/en-us/rls_options_overview.htm)

### Inferences
- Para um painel nativo (não embarcado de terceiro), o equivalente ao "app owns data" é o próprio back-end do ENSPACE aplicar as regras de visibilidade de tarefa que já valem nas listas, na mesma consulta que gera os números do painel.
- Os 3 riscos que os fornecedores apontam no embed valem para um painel nativo: identidade reaproveitada entre tenants (Looker), filtro só na interface (Metabase, "hiding doesn't restrict") e conta de serviço que não carrega o usuário final (Power BI).

### Gaps
- Não abri a doc do Sisense sobre embed com SSO ou JWT; a página de Data Access Security não fala de usuário embarcado.
- Não abri a doc do Metabase de modular ou full app embedding com SSO (mapeamento de grupos e atributos).

## 3. Princípios de segurança e privacidade: menor privilégio, risco de inferência por agregado, métrica de desempenho por pessoa (LGPD, GDPR, ICO, EDPB, ANPD)

### Takeaway
Menor privilégio e deny by default pedem que o painel calcule só sobre o que a pessoa pode ver, com a checagem no servidor. Total e contagem podem revelar o que está escondido (subtração entre 2 números, célula pequena), e o setor de saúde dos EUA suprime contagens de 1 a 10. Métrica de produtividade por pessoa é monitoramento de trabalhador: ICO e WP29 pedem necessidade, proporcionalidade, transparência e avaliação de impacto; no Brasil, a LGPD dá os princípios e a ANPD ainda não tem guia próprio sobre relações de trabalho.

### Cited Findings

**Menor privilégio e autorização**
- NIST SP 800-53 Rev. 5, AC-6 (Least Privilege): empregar o menor privilégio, liberando só os acessos necessários para as tarefas atribuídas. Inclui os reforços AC-6(1) a AC-6(10), entre eles AC-6(7) Review of User Privileges — [CSF Tools, espelho do texto do NIST SP 800-53 r5 AC-6](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-6/); catálogo oficial no [NIST CPRT](https://csrc.nist.gov/projects/cprt/catalog) (atualizado em 2026-02-19; o texto do controle não abriu pela ferramenta)
- OWASP Authorization Cheat Sheet: dar só o privilégio mínimo e revisar contra o acúmulo ("privilege creep"); negar por padrão e não confiar no padrão do framework; validar a permissão em toda requisição ("an attacker only needs to find one way in"); nunca decidir acesso no cliente, sempre no servidor; checar cada objeto, não só o tipo (IDOR); preferir ABAC ou ReBAC a RBAC; tratar a falha de autorização como evento normal, com resposta simples e lógica centralizada — [OWASP Cheat Sheet Series, Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

**Inferência e agregação**
- A política de supressão de células da CMS (Medicare e Medicaid) proíbe publicar células com valor de 1 a 10 (zero pode). Também proíbe qualquer célula, percentual ou fórmula que permita deduzir um valor de 1 a 10 a partir de outros números publicados. No exemplo da própria página, suprimir só a faixa 85+ não basta, porque o total da coluna menos as outras faixas devolve 6; é preciso suprimir uma 2ª célula (supressão complementar) ou juntar faixas. Versão de 2024-01-26 — [ResDAC, CMS Cell Size Suppression Policy](https://resdac.org/articles/cms-cell-size-suppression-policy)
- Ataque de diferença: 2 agregados cujo conjunto difere em 1 pessoa revelam o valor dela; contagens também caem nisso, e agregado sobre 1 linha (média, soma, mínimo, máximo) devolve o valor da própria linha. Limite mínimo por consulta não basta, porque o ataque está na relação entre consultas; as defesas citadas são limite mínimo com controle de sobreposição, auditoria de consulta, ruído e privacidade diferencial — [Open Exam Prep, CIPT 7.1 Minimizing Privacy Risk from Aggregation and Inference](https://open-exam-prep.com/study-guides/cipt/use-controls-pets/aggregation-inference-risk); [Virtual Labs, Statistical Inference Control](https://ds-amrt.vlabs.ac.in/exp/statistical-inference-control/theory.html) (fontes secundárias, lidas no resumo da busca; as primárias citadas são Denning 1979 e Dinur e Nissim 2003)

**Monitoramento de trabalhador e métrica por pessoa**
- A ICO publicou a guia final "Employment practices and data protection: monitoring workers" em 2023-10-03 — [Inside Privacy (Covington)](https://www.insideprivacy.com/data-privacy/uk-information-commissioners-office-releases-rew-guidance-for-monitoring-at-work/); [Data Protection Report](https://www.dataprotectionreport.com/2023/10/uk-information-commissioners-office-publishes-final-guidance-on-employee-monitoring/)
- A página da ICO diz hoje que a guia está em revisão por causa do Data (Use and Access) Act. Ela vale para empregador e para qualquer relação de trabalho, inclusive gig economy, e usa "must" para obrigação legal, "should" para boa prática esperada e "could" para opção — [ICO, Monitoring workers](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/employment/monitoring-workers/)
- Pelos resumos de escritórios: a guia cita como exemplo de monitoramento ferramentas de produtividade que registram como o trabalhador usa o tempo; o monitoramento precisa ser necessário, proporcional, transparente e compatível com o que o trabalhador espera; a ICO recomenda DPIA antes de qualquer monitoramento, mesmo quando não é obrigatória, e pede registrar a opinião dos trabalhadores; DPIA é obrigatória em casos de alto risco, como monitoramento que pode levar a perda financeira (gestão de desempenho); pagar com base só em monitoramento automatizado de produtividade cai no Art. 22 do UK GDPR — [HFW](https://www.hfw.com/insights/ICO-Publishes-Guidance-on-Monitoring-Workers); [Cooley](https://cdp.cooley.com/new-uk-guidance-on-workplace-monitoring/); [Baker McKenzie](https://connectontech.bakermckenzie.com/ico-guidance-on-monitoring-of-workers-key-takeaways-for-employers/); [Simmons & Simmons](https://www.simmons-simmons.com/en/publications/clntro05s00v4udeo8l5vndzs/employee-monitoring-updated-ico-guidance) (fontes secundárias)
- Opinião 2/2017 do Grupo de Trabalho do Art. 29 (WP249, antecessor do EDPB) sobre tratamento de dados no trabalho: para cada cenário, o empregador responde 4 perguntas (necessidade e base legal, justiça com o empregado, proporcionalidade, transparência) antes de começar; o método precisa ser o menos intrusivo possível; o consentimento quase nunca vale, pelo desequilíbrio entre empregador e empregado; DPIA quando o risco é alto — [A&L Goodbody](https://www.algoodbody.com/insights-publications/article-29-working-party-opinion-on-data-processing-at-work); [RPC](https://www.rpclegal.com/snapshots/data-protection/data-protection-working-party-adopts-opinion-22017-on-data-processing-at-work/); [Wikborg Rein](https://www.wr.no/en/news/the-wp29-opinion-2-2017-on-data-processing-at-work) (fontes secundárias)
- LGPD, Art. 6: finalidade (propósito legítimo, específico, explícito e informado), adequação, necessidade ("limitação do tratamento ao mínimo necessário"), transparência, segurança (proteger de acessos não autorizados) e responsabilização. Art. 20: direito de revisão de decisão tomada só por tratamento automatizado, inclusive a que define o perfil profissional. Art. 38: a ANPD pode exigir relatório de impacto. Art. 46: medidas técnicas e administrativas contra acessos não autorizados — [Planalto, Lei 13.709/2018](https://www.planalto.gov.br/ccivil_03/_ato2015-2018/2018/lei/l13709.htm)
- ANPD: não achei guia da ANPD sobre dados de empregados ou monitoramento. Em 2026-07-09, o CNPD (Conselho Nacional de Proteção de Dados) enviou à ANPD 6 temas prioritários para a Agenda Regulatória 2027-2028, entre eles "Tratamento de dados pessoais nas relações de trabalho", citando monitoramento de trabalhadores, assimetria entre empregador e trabalhador, limites do consentimento, automação e IA — [gov.br/anpd, CNPD encaminha contribuições prioritárias para a Agenda Regulatória 2027-2028](https://www.gov.br/anpd/pt-br/cnpd/cnpd-encaminha-contribuicoes-prioritarias-para-a-agenda-regulatoria-da-anpd-2027-2028)
- A Agenda Regulatória 2025-2026 da ANPD (Resolução 23/2024, 16 iniciativas, depois com 3 temas do ECA Digital) não traz item específico de relações de trabalho nos resultados da busca — [Mattos Filho, ANPD publica Agenda Regulatória 2025-2026](https://www.mattosfilho.com.br/unico/anpd-agenda-regulatoria-2025/); [Migalhas](https://www.migalhas.com.br/coluna/migalhas-de-protecao-de-dados/423103/destaques-da-agenda-regulatoria-2025-2026-da-anpd) (fontes secundárias)

### Inferences
- Um painel de tarefas com filtro por responsável e poucas pessoas por equipe é o caso da célula pequena: "1 tarefa atrasada de Fulano" identifica a pessoa, e "total da equipe menos o que eu vejo" revela o resto. Se o painel mostra o total de tarefas que a pessoa não pode abrir, a diferença entre os 2 números é exatamente o dado protegido.
- Ranking ou média de conclusão por pessoa é métrica de produtividade por trabalhador. Pelas fontes da ICO e do WP29, exige finalidade declarada, transparência para quem é medido, o caminho menos intrusivo (por equipe antes de por pessoa) e avaliação de impacto; sob a LGPD, os princípios de finalidade e necessidade cobrem o mesmo ponto e, se o número alimenta decisão automática sobre a pessoa, entra o Art. 20.
- O cliente do ENSPACE é o controlador dos dados dos trabalhadores dele; o ENSPACE, como fornecedor, influencia o risco pelo padrão do produto (o que o painel mostra por pessoa sem configuração).

### Gaps
- Não abri o texto oficial do AC-6 no NIST (o CPRT não renderizou); usei o espelho do CSF Tools. Também não abri controles ligados a agregação e inferência (como AC-23 Data Mining Protection), por isso ficam sem citação.
- Não abri as subpáginas da ICO com a regra detalhada (DPIA, base legal, produtividade); os pontos vêm de resumos de escritórios.
- Não abri o WP249 original nem achei documento do EDPB que o substitua; os pontos vêm de resumos.
- Não achei fonte primária sobre limite mínimo de células em produto SaaS de tarefas; a referência numérica (1 a 10) é da saúde pública dos EUA.

## 4. UX de permissão negada e dado parcial em painéis ("você vê X de Y", esconder x desabilitar)

### Takeaway
Não há norma nem estudo empírico que feche a questão; a convenção é esconder o que a pessoa nunca vai usar, desabilitar com explicação o que ela pode vir a ter, e nunca deixar widget vazio ou quebrado sem explicar o motivo. Nos BI, a falta de permissão costuma aparecer como vazio ou erro, e é disso que os usuários reclamam.

### Cited Findings
- Vitaly Friedman (2024-05-21): desabilitar quando a pessoa deve saber que o recurso existe mas não está disponível; esconder quando o valor é irrelevante agora; nunca esconder botão principal ou filtro-chave por padrão; explicar por que está desabilitado e como liberar; evitar salto de layout ao trocar a visibilidade. O teste citado (de Sam Solomon): essa pessoa vai poder usar esse elemento algum dia? Sim, desabilite; não, esconda. A lista de "esconder" inclui permissões e controles de acesso — [Smashing Magazine, Hidden vs. Disabled In UX](https://smashingmagazine.com/2024/05/hidden-vs-disabled-ux/)
- O design system da Emarsys desabilita a ação restrita com tooltip que diz a permissão necessária e usa, para página inteira restrita, um estado vazio "Permission Denied" com a permissão exigida e um caminho de volta; diz que não há regra fixa sobre o que desabilitar e o que esconder — [Emarsys Design System, Permission handling](https://designsystem.emarsys.net/docs/patterns/permission-handling/) (lido no resumo da busca)
- Pedido de melhoria no Harness: quando o escopo de dados restringe, o widget parece só não carregar — [Harness Ideas, Show lack of permissions or data in a dashboard](https://ideas.harness.io/feature-request/p/show-lack-or-permissions-or-data-when-user-has-no-access-to-data-in-a-dashboard) (lido no resumo da busca)
- Jakob Nielsen registra que não há dado empírico definitivo sobre qual padrão (esconder ou desativar) funciona melhor — [UX Tigers, Inactive buttons](https://www.uxtigers.com/post/inactive-buttons) (lido no resumo da busca)
- No Power BI, um relatório que referencia dado protegido mostra a mesma mensagem de campo apagado ou inexistente, e para o usuário "it looks like the report is broken" — [Microsoft Learn, RLS with Power BI](https://learn.microsoft.com/en-us/fabric/security/service-admin-row-level-security)
- No Looker, o tile sem acesso ao modelo aparece em branco ou com erro — [Looker docs, Access control and permission management](https://docs.cloud.google.com/looker/docs/access-control-and-permission-management)
- No Metabase, o atributo que não casa devolve resultado vazio, sem aviso de permissão — [Metabase docs, Row and column security](https://www.metabase.com/docs/latest/permissions/row-and-column-security)

### Inferences
- "Você vê X de Y" entrega Y, o total que inclui o que a pessoa não pode ver; com 2 recortes, Y menos X é o dado protegido (ver o ataque de diferença na seção 3). Uma alternativa sem vazamento é dizer o escopo em texto ("Mostrando as tarefas que você pode ver") em vez do número total.
- Painel fixo com escopo pela permissão: o estado vazio precisa separar "não há tarefas" de "não há tarefas que você possa ver", sem contar as escondidas.

### Gaps
- Não achei guia de UX autoritativo (NN/g, Material, Carbon, Atlassian) sobre o indicador "X de Y" em painel com dado parcial; o tema fica com as fontes de convenção acima.
- As fontes da Emarsys, do Harness e da UX Tigers foram lidas pelo resumo da busca, sem abrir a página.
